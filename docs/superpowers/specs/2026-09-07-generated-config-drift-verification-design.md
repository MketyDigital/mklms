# MkLMS Generated Configuration + Read-Only Drift Verification Design

Date: 2026-09-07
Status: Approved design, implementation not started

## Purpose

Combine Phase 2 and Phase 3 of the managed-installation roadmap into one safe architectural batch:

1. generate temporary per-installation Cloudflare Wrangler configuration from validated installation manifests; and
2. extend the existing Cloudflare verification workflow so a known installation can be checked against live Cloudflare metadata using read-only API calls only.

This batch must not provision, deploy, mutate, migrate, or promote any production infrastructure.

## Non-negotiable production safety boundary

The current Starpips production installation remains untouched throughout this batch.

Current production branch:

- `production/starpips`
- pinned commit: `230819f4c5be0d9e13ce23b404c23d57115aae8b`

The live Starpips site at `learn.starpipsforex.com` continues using its existing Worker, media Worker, database, Hyperdrive bindings, R2 bucket, rate-limit namespaces, secrets, billing configuration, domain, and application behavior.

This batch may not:

- update `production/starpips`
- deploy any Worker
- call Cloudflare POST, PUT, PATCH, or DELETE APIs
- create or modify R2 buckets
- create or modify Hyperdrive resources
- create or modify rate-limit namespaces
- create or modify DNS records or custom domains
- create, rotate, or update secrets
- connect to or mutate PostgreSQL
- run migrations against any live/customer database
- change Starpips application runtime behavior
- create `production/mkety-academy` or customer production branches

## Architectural principle

Installation manifests remain the source of truth for non-secret per-installation infrastructure identity.

Generated Wrangler configuration is an ephemeral build artifact derived from a validated manifest. It is not manually edited and is not the source of truth.

The architecture is:

```text
deploy/installations/<installation>.json
                |
                v
      local manifest validation
                |
                v
 reusable config generation templates
                |
                v
.generated/<installation>/
  app.wrangler.jsonc
  media.wrangler.jsonc
                |
          no deployment
                |
                +----> repository equivalence checks
                |
                +----> read-only Cloudflare drift checks
```

## Generation contract

Only a concrete, `deployable: true` installation manifest may be generated by the production-equivalent generation command.

Example/template manifests remain non-deployable. A separate explicitly named example command may render them for tests/docs if useful, but no production-oriented command may accept them.

### Generated application config

The generated app config must preserve the reusable MkLMS runtime shape while replacing installation-specific resource identifiers from the manifest.

Expected generated app values include:

- Worker name = manifest `appWorker`
- main = `.open-next/worker.js`
- compatibility date = existing supported date unless intentionally versioned later
- `nodejs_compat` compatibility flag
- build command = `npm run cf:build`
- assets directory/binding = existing MkLMS values
- observability enabled
- Hyperdrive bindings:
  - `HYPERDRIVE_FRESH` -> manifest `hyperdrive.freshId`
  - `HYPERDRIVE_CACHED` -> manifest `hyperdrive.cachedId`
- R2 binding:
  - `APP_STORAGE_BUCKET` -> manifest `r2Bucket`
- five required rate-limit bindings using manifest namespace IDs with existing limits/periods

No secret text bindings are emitted by the generator.

### Generated media config

The generated media config must preserve:

- main = `src/index.ts`
- compatibility date
- observability enabled
- Worker name = manifest `mediaWorker`
- R2 binding `MEDIA_BUCKET` -> manifest `r2Bucket`

No secret values are generated.

## Determinism requirements

Given the same manifest and generator version, output must be byte-stable except for an optional final newline.

Generation must:

- use stable property ordering
- use deterministic indentation
- never include timestamps
- never include machine-specific paths
- never include secret values
- never access the network

## Starpips equivalence gate

Before generated configuration can be considered production-equivalent, Starpips generated output must match the current committed Starpips Wrangler configuration semantically.

Comparison must account for JSONC formatting/comments but require equality for the relevant supported fields.

The gate checks at minimum:

### App Worker

- name `mklms`
- main `.open-next/worker.js`
- compatibility date `2026-08-30`
- compatibility flags `["nodejs_compat"]`
- build command `npm run cf:build`
- assets directory `.open-next/assets`
- assets binding `ASSETS`
- observability enabled
- Hyperdrive IDs
- R2 bucket `spf-media`
- all five rate-limit namespace IDs and simple policies

### Media Worker

- name `mklms-media-delivery`
- main `src/index.ts`
- compatibility date `2026-08-30`
- observability enabled
- media R2 bucket `spf-media`

The existing committed Starpips Wrangler files are comparison inputs only and must not be rewritten in this batch.

## Read-only live drift verification

The existing manual Cloudflare verifier becomes installation-aware.

The workflow remains `workflow_dispatch` only.

It accepts one installation selector restricted to concrete, known deployable manifests. Initially this is `starpips` only because Mkety/customer resources do not yet exist.

The workflow:

1. checks required GitHub secrets exist;
2. reads the selected manifest from the repository;
3. validates the manifest locally;
4. performs Cloudflare authenticated GET requests only;
5. reads application Worker settings/deployments;
6. reads media Worker settings/deployments when API endpoint support is available;
7. compares safe non-secret live metadata against manifest/generated expectations;
8. fails on detected drift;
9. prints only safe identifiers/types/status metadata.

## Allowed Cloudflare operations

Only GET requests are allowed.

Examples of acceptable API reads include:

- Worker settings
- Worker deployments

If an endpoint needed for a comparison is not available or returns metadata insufficient for a safe assertion, the workflow reports that field as `not verifiable` rather than inferring or mutating anything.

## Forbidden workflow behavior

The workflow must contain no:

- POST
- PUT
- PATCH
- DELETE
- `wrangler deploy`
- `opennextjs-cloudflare deploy`
- `wrangler secret`
- R2 write commands
- DNS mutation commands
- database/migration commands

Its GitHub permissions remain minimal (`contents: read`).

## Drift comparison model

The verifier compares only non-secret metadata that is both declared and observable.

Required Starpips comparisons when available:

- app Worker name
- app R2 binding name/type
- app Hyperdrive binding names/types and resource IDs if Cloudflare exposes them safely
- required rate-limit binding names/types and namespace IDs if exposed safely
- media Worker name
- media R2 binding name/type
- existence/readability of latest deployments

Secret bindings may be checked for required binding names/types only. Secret values must never be requested, printed, compared, or stored.

## Handling API limitations

Cloudflare may expose some binding types without underlying resource IDs in a given endpoint response.

The verifier therefore uses three outcomes per field:

- `match` — observed value equals expected value
- `drift` — observed value is available and differs
- `not_verifiable` — API does not expose enough information safely

`drift` fails the verification.

`not_verifiable` does not silently pass as equality; it is reported explicitly and remains a limitation for future Phase 4 safeguards.

## Local commands

Add commands conceptually equivalent to:

```text
npm run installation:validate
npm run installation:generate -- starpips
npm run installation:compare-starpips
```

All three commands are local-only and perform no external calls.

Generated files go under `.generated/starpips/`.

## Security model

- manifests contain no secret values
- generator output contains no secret values
- `.generated/` is ignored
- Cloudflare API token/account ID remain GitHub Actions secrets
- workflow logs never print token/account ID values
- secret bindings are logged by name/type only
- workflow cannot be triggered by push or pull_request
- workflow is constrained to known installation IDs rather than arbitrary Worker names or API URLs

## Test strategy

Use TDD.

Tests must cover at minimum:

1. generation refuses unknown installation IDs;
2. generation refuses example/template manifests in production mode;
3. generated app config matches the Starpips manifest identifiers;
4. generated media config matches the Starpips manifest identifiers;
5. output is deterministic;
6. generated files contain no secret-like keys/values;
7. `.generated/` is ignored by git;
8. Starpips generated app config is semantically equivalent to committed `wrangler.jsonc` for supported fields;
9. Starpips generated media config is semantically equivalent to committed media Wrangler config;
10. existing Starpips Wrangler files are not modified;
11. workflow remains manual-only;
12. workflow has `contents: read` only;
13. workflow exposes a constrained installation selector;
14. workflow uses only GET Cloudflare requests;
15. workflow contains no deployment/provision/migration commands;
16. workflow validates selected manifest before Cloudflare reads;
17. drift logic distinguishes match/drift/not_verifiable;
18. secret values cannot reach logs;
19. all existing MkLMS tests/build/package dry-runs remain green.

## Failure behavior

Generation failure must leave no partial deployable output, or it must clean the target installation generation directory before exiting non-zero.

Drift verification fails non-zero on:

- invalid selected installation
- invalid manifest
- missing Cloudflare credentials
- authentication failure
- Worker not found
- explicit observable drift

API limitations become explicit `not_verifiable` output and do not trigger mutation or fallback guesses.

## Rollback

Because this batch has no production writes, rollback is repository-only:

- revert the Phase 2+3 merge from `main` if necessary
- leave `production/starpips` untouched
- delete disposable `.generated/` output

No Cloudflare/database/storage rollback is expected because no such writes are permitted.

## Success criteria

This combined batch is complete when:

- a concrete installation can generate deterministic app/media Wrangler config locally;
- Starpips generated config passes semantic equivalence against current committed Starpips config;
- live Starpips can be checked through a manual GET-only installation-aware workflow;
- observable drift fails clearly;
- unverifiable fields are reported honestly;
- no secrets are exposed;
- no live infrastructure is changed;
- `production/starpips` remains unchanged;
- all existing MkLMS CI/build/dry-run checks pass.

## Explicit next boundary

After this batch, Phase 4 may design controlled provisioning/deployment for new isolated installations.

Phase 4 must remain a separate design/spec/approval cycle because it introduces real Cloudflare/database/storage writes.
